0130초 요약

  • 용도 — 60여 종의 표준 학술 벤치마크(수백 개 서브태스크)를 통일된 방식으로 실행해 모델 점수를 낸다. HuggingFace Open LLM Leaderboard의 백엔드이고, NVIDIA·Cohere·BigScience·BigCode·Nous Research·Mosaic ML 등이 내부적으로 쓴다.
  • 목표 — 프롬프트를 공개해 재현 가능하고 비교 가능한 평가를 만드는 것. 이 프로젝트의 존재 이유는 벤치마크 개발이 아니라 "같은 조건"의 확보다.
  • 사용법 — lm-eval run --model <백엔드> --model_args ... --tasks ... 한 줄이 기본. 모델 백엔드는 별도 설치(pip install "lm_eval[vllm]" 등), 태스크는 YAML로 정의된다.
  • 확장점 — 태스크는 YAML로 추가하고(코드 없이 가능), 모델은 LM 클래스를 상속해 3개 메서드만 구현하면 붙는다.
  • 주의 — 만든 사람들 스스로 논문 간 점수 비교를 권장하지 않는다. 프롬프트·few-shot 설정이 조금만 달라도 점수가 흔들리기 때문이다.

02이게 정확히 무슨 도구인가

이름의 "harness"가 오해를 부른다. 여기서 하네스는 에이전트를 운용하는 실행 환경이 아니라 모델을 벤치마크에 물려 돌리는 시험대를 뜻한다. 전기 회로 시험용 배선 다발(wire harness)에 가까운 쪽이다.

구체적으로 하는 일은 네 단계다.

  1. 데이터셋에서 문제를 꺼낸다
  2. 정해진 템플릿으로 프롬프트를 만든다 (few-shot 예제 포함)
  3. 모델에 요청을 보낸다 — 요청 타입은 로그확률 계산이거나 텍스트 생성이다
  4. 응답에서 답을 추출해 채점하고 집계한다

3번의 요청 타입이 이 도구의 성격을 결정한다. 객관식 문제는 각 보기의 로그확률을 비교해 채점하므로 생성이 필요 없다. 그래서 로그확률을 주지 않는 모델(대부분의 챗 API)은 생성형 태스크만 돌릴 수 있다.

output_type동작
multiple_choice보기별 로그확률을 비교해 정답 선택. 생성 없음
loglikelihood주어진 이어붙임 문자열의 로그확률 계산
loglikelihood_rolling긴 문서 전체의 로그확률 — perplexity 계열 태스크용
generate_until정지 조건까지 텍스트 생성 후 후처리·채점

03무엇을 하려는 프로젝트인가

README에 프롬프트 설계 원칙이 우선순위 목록으로 명시돼 있다. 이 목록이 프로젝트의 의도를 가장 잘 드러낸다.

  1. LLM을 학습시키는 사람들 사이에 합의된 절차가 있으면 그것을 따른다
  2. 명확하고 모호하지 않은 공식 구현이 있으면 그것을 따른다
  3. LLM을 평가하는 사람들 사이에 합의가 있으면 그것을 따른다
  4. 흔한 구현이 여럿이고 합의가 없으면, 그중 선호안을 택하되 학습 논문에 쓰인 구현을 우선한다

즉 "더 나은 평가 방법을 발명한다"가 아니라 "이미 쓰이는 방법을 정확히 재현한다"가 목표다. 원래 출발점도 GPT-3 논문(Language Models are Few-Shot Learners)의 결과와 비교하는 것이었다.

그러면서도 프로젝트 스스로 한계를 인정한다. 다른 그룹의 절차와 최대한 맞추려는 이유가 "사람들이 우리가 말려도 어차피 논문 간 점수를 비교하기 때문에, 그때 생기는 피해를 줄이려는 것"이라고 적혀 있다. 비교 가능성을 만들려는 도구가 비교의 위험성을 함께 경고한다는 점이 이 프로젝트의 태도다.

04구조 — 3개 층

코드를 읽기 전에 이 세 층만 구분하면 전체가 잡힌다.

모델 층 (LM 인터페이스)
토크나이저에 구애받지 않는 추상 인터페이스. 구현해야 할 메서드는 loglikelihood, generate_until, loglikelihood_rolling 세 개뿐이다. HF·vLLM·SGLang·OpenAI 호환 API·NeMo·Megatron-LM·OpenVINO·llama.cpp 등이 모두 이 인터페이스의 구현체다.
태스크 층 (YAML)
데이터셋 경로, 프롬프트 템플릿(Jinja2), 정답 추출 방식, few-shot 설정, 메트릭이 한 YAML 파일에 들어간다. 파이썬 코드 없이 새 태스크를 만들 수 있다. 태스크는 개별 subtask, 묶음인 group(예: mmlu 안에 57개), 분류용 tag로 조직된다.
후처리·채점 층 (filter + metric)
모델 출력에서 답을 뽑아내는 필터 파이프라인과 채점 메트릭. 필터는 여러 파이프라인을 동시에 걸 수 있어서 같은 출력에 대해 엄격한 추출과 느슨한 추출의 점수를 함께 낼 수 있다.

기본 제공 메트릭

acc, acc_norm(길이 정규화), acc_mutual_info, perplexity, word_perplexity, byte_perplexity, bits_per_byte, matthews_corrcoef, f1, bleu, chrf, ter. 집계 함수는 mean, median, perplexity, weighted_perplexity, bits_per_byte.

05설치

2025년 12월에 설치 방식이 바뀌었다

기본 패키지에 더 이상 torch·transformers가 들어 있지 않다. 모델 백엔드를 따로 설치해야 한다. 예전 문서나 블로그를 따라 하면 백엔드 없이 설치돼 실행이 안 된다.

git clone --depth 1 https://github.com/EleutherAI/lm-evaluation-harness
cd lm-evaluation-harness
pip install -e .

# 백엔드는 별도 (필요한 것만)
pip install "lm_eval[hf]"      # HuggingFace transformers
pip install "lm_eval[vllm]"    # vLLM
pip install "lm_eval[api]"     # OpenAI/Anthropic/로컬 OpenAI 호환 서버
pip install "lm_eval[hf,vllm,api]"   # 동시 설치

기본 의존성은 가볍다 — datasets, numpy, evaluate, jinja2, sacrebleu, scikit-learn, sqlitedict, rouge-score 등. 태스크별 추가 extras도 따로 있다(math, ifeval, longbench, ruler, multilingual 등).

06CLI 기본 사용법

2025년 12월 리팩터링으로 서브커맨드 체계가 됐다. 기존 단일 명령 형식도 계속 동작한다 — lm-eval --model hf ...를 치면 run이 자동으로 끼워진다.

명령용도
lm-eval run평가 실행
lm-eval ls태스크·그룹·서브태스크·태그 목록 조회
lm-eval validate태스크 설정 검증 — 실행 전 문법·데이터셋 접근·메트릭·필터·템플릿 확인
 
# 어떤 태스크가 있는지
lm-eval ls tasks
lm-eval ls groups

# 기본 실행
lm-eval run --model hf --model_args pretrained=gpt2 --tasks hellaswag

# few-shot 5개
lm-eval run --model hf --model_args pretrained=gpt2 --tasks arc_easy --num_fewshot 5

# 결과와 모델 출력까지 저장
lm-eval run --model hf --model_args pretrained=gpt2 --tasks hellaswag \
    --output_path ./results/ --log_samples

# 실행 전 태스크 검증
lm-eval validate --tasks arc_easy,arc_challenge,hellaswag

알아둘 만한 플래그

플래그설명
--tasks / -t태스크 또는 그룹 이름. 와일드카드 지원 (lambada_openai_mt_*)
--batch_size auto디바이스에 맞는 최대 배치를 자동 탐색. auto:4는 4회 재계산
--limit / -L태스크당 예제 수 제한. 테스트 전용 — 이 값으로 나온 점수는 보고하면 안 된다
--log_samples / -s모델 입출력 전부 저장. 사후 분석의 출발점
--predict_only / -x생성만 하고 채점은 건너뜀. 신뢰할 수 없는 코드 실행이 걸린 태스크나 별도 채점 파이프라인이 있을 때
--apply_chat_template챗 템플릿 적용. 켜면 few-shot이 자동으로 멀티턴 형식이 된다
--write_out / -w앞쪽 몇 개 문서의 프롬프트를 출력. 새 태스크를 만들면 반드시 이걸로 눈으로 확인할 것
--seedpython,numpy,torch,fewshot 순. 기본값 0,1234,1234,1234
--include_path외부 태스크 YAML 디렉터리 추가
--trust_remote_codeHF Hub의 원격 코드 실행 허용
--confirm_run_unsafe_code임의 파이썬을 실행하는 태스크를 돌릴 때 필요한 명시적 확인

환경 변수

LMEVAL_LOG_LEVEL(로그 레벨), LM_HARNESS_CACHE_PATH(요청 캐시 경로), HF_TOKEN, TOKENIZERS_PARALLELISM.

07백엔드별 실행

HuggingFace transformers

lm_eval --model hf \
    --model_args pretrained=EleutherAI/pythia-160m,revision=step100000,dtype="float" \
    --tasks lambada_openai,hellaswag \
    --device cuda:0 \
    --batch_size auto:4

--model_args에 넣은 값은 그대로 생성자에 전달된다. 즉 AutoModel로 할 수 있는 건 다 된다 — 로컬 경로(pretrained=/path/to/model), PEFT 어댑터(peft=...), 4bit 로딩(load_in_4bit=True), GPTQ(gptqmodel=True), delta 가중치 등.

멀티 GPU

방식명령
데이터 병렬
(GPU마다 모델 전체 복사)		accelerate launch -m lm_eval --model hf ...
FSDP 샤딩과 함께 쓸 수 없다
모델 샤딩
(한 GPU에 안 들어갈 때)		런처 없이 실행하고 --model_args parallelize=True
둘 다accelerate launch --multi_gpu --num_processes N -m lm_eval ... parallelize=True
텐서 병렬 (PyTorch 네이티브)torchrun --nproc-per-node=4 -m lm_eval --model_args ...,tp_plan=auto
parallelize=True와 배타적. KV 헤드 수가 TP degree로 나누어떨어져야 한다

멀티노드는 네이티브로 지원하지 않는다. 외부 추론 서버를 띄워 그쪽에 요청을 보내거나, 분산 프레임워크와 직접 통합하라고 안내한다.

vLLM

lm_eval --model vllm \
    --model_args pretrained={model},tensor_parallel_size={GPUs_per_model},dtype=auto,gpu_memory_utilization=0.8,data_parallel_size={replicas} \
    --tasks lambada_openai \
    --batch_size auto
  • --batch_size auto를 쓰는 것이 권장된다 — vLLM의 continuous batching을 살리기 위해서다
  • data_parallel_size>1은 복제본마다 ray 액터를 띄우므로 pip install ray가 필요하다
  • max_model_len=4096 같은 값을 넘기면 auto 배치에서 OOM을 피하거나 속도를 얻을 수 있다
vLLM 결과는 HF와 다를 수 있다

프로젝트는 HuggingFace 구현을 기준(reference)으로 삼고, vLLM 결과의 타당성을 대조하는 스크립트(scripts/model_comparator.py)를 제공한다. 속도 때문에 vLLM으로 점수를 냈다면, 보고 전에 HF와 대조해 두는 편이 안전하다.

OpenAI 호환 로컬 서버 — 사내 환경에서 가장 실용적인 경로

lm_eval --model local-completions \
    --tasks gsm8k \
    --model_args model=facebook/opt-125m,base_url=http://{host}:8000/v1/completions,num_concurrent=1,max_retries=3,tokenized_requests=False,batch_size=16

이미 vLLM을 OpenAI 호환 서버로 띄워 운영 중이라면, 평가를 위해 모델을 다시 로드할 필요 없이 운영 중인 그 서버를 그대로 평가 대상으로 붙일 수 있다. 대형 모델은 이 방식이 권장된다.

모델 타입 이름은 local-completions(Completions API) 또는 local-chat-completions(ChatCompletions API)다. 챗 계열은 로그확률을 주지 않으므로 generate_until 태스크만 가능하다.

그 밖의 백엔드

sglang, nemo_lm, megatron_lm, openvino, ipex, habana, neuronx, gguf/ggml(llama.cpp), mamba_ssm, winml(ONNX Runtime GenAI, NPU 포함), watsonx_llm, steered(스티어링 벡터 적용 HF 모델), 상용 API는 openai-completions·anthropic-chat·litellm 등.

08결과 저장·캐싱·재개

플래그동작
--output_path결과 JSON 저장 위치. --log_samples를 쓰면 필수
--log_samples모델 입출력 전부 기록
--use_cache <DIR>모델 응답을 SQLite에 캐싱. 같은 (모델, 태스크) 조합을 재실행하면 이미 평가한 샘플을 건너뛴다

--hf_hub_log_args결과·샘플을 HF Hub 데이터셋으로 푸시
--wandb_argsW&B 로깅 (lm_eval[wandb] 필요)
캐시는 rank에 종속된다

중단 후 재개할 때는 같은 GPU 개수로 다시 시작해야 한다. GPU 수가 바뀌면 캐시가 어긋난다.

09YAML 설정 파일

플래그가 길어지면 설정 파일로 옮길 수 있다. CLI 인자가 설정 파일 값을 덮어쓴다.

# eval_config.yaml
model: hf
model_args:
  pretrained: gpt2
  dtype: float32

tasks:
  - hellaswag
  - arc_easy

num_fewshot: 0
batch_size: auto
device: cuda:0

output_path: ./results/gpt2/
log_samples: true
lm-eval run --config eval_config.yaml

# 설정은 두고 일부만 덮어쓰기
lm-eval run --config eval_config.yaml --tasks mmlu --limit 100

설정 키는 CLI 인자와 1:1로 대응한다. 실행 조건을 결과와 함께 버전 관리하기 좋은 형태다 — 재현성이 목적인 도구에서 이 파일이 사실상 실험 기록이 된다.

10Python API

진입점이 세 가지다. 대부분은 simple_evaluate()면 된다.

import lm_eval

results = lm_eval.simple_evaluate(
    model="hf",
    model_args="pretrained=gpt2,dtype=float32",
    tasks=["hellaswag", "arc_easy"],
    num_fewshot=5,
    batch_size=8,
    device="cuda:0",
)

print(results["results"])

이미 만들어 둔 모델 객체를 그대로 넘길 수도 있다.

from lm_eval.models.huggingface import HFLM

lm = HFLM(pretrained="gpt2", batch_size=16)
results = lm_eval.simple_evaluate(model=lm, tasks=["hellaswag"], num_fewshot=0)

반환 딕셔너리에는 results(메트릭과 표준오차), configs(태스크 설정), versions(태스크 버전), n-shot, n-samples, 그리고 log_samples=True면 samples가 들어 있다. versions가 함께 남는 점이 중요하다 — 태스크 정의가 바뀌면 점수가 달라지므로, 버전 없이 점수만 남기면 나중에 비교가 불가능해진다.

더 낮은 층위가 필요하면 evaluate()에 미리 만든 task_dict를 넘긴다. 설정 파일 기반으로는 EvaluatorConfig를 쓴다.

11태스크 직접 만들기

YAML 하나면 된다. 아래는 저장소에 실제로 들어 있는 객관식 태스크 정의다.

# lm_eval/tasks/arc/arc_easy.yaml
tag:
  - ai2_arc
task: arc_easy
dataset_path: allenai/ai2_arc
dataset_name: ARC-Easy
output_type: multiple_choice
training_split: train
validation_split: validation
test_split: test
doc_to_text: "Question: {{question}}\nAnswer:"
doc_to_target: "{{choices.label.index(answerKey)}}"
doc_to_choice: "{{choices.text}}"
should_decontaminate: true
doc_to_decontamination_query: "Question: {{question}}\nAnswer:"
metric_list:
  - metric: acc
    aggregation: mean
    higher_is_better: true
  - metric: acc_norm
    aggregation: mean
    higher_is_better: true
metadata:
  version: 1.0

doc_to_text·doc_to_target은 Jinja2 템플릿이다. 데이터셋의 각 행이 doc으로 들어와 필드를 그대로 참조한다.

필터 파이프라인 — 이 도구에서 가장 이식할 가치가 있는 설계

생성형 태스크는 모델이 뱉은 문자열에서 답을 뽑아내야 한다. 아래 gsm8k 정의는 같은 출력에 두 개의 추출 파이프라인을 동시에 걸어 두 점수를 함께 낸다.

# lm_eval/tasks/gsm8k/gsm8k.yaml (발췌)
output_type: generate_until
doc_to_text: "Question: {{question}}\nAnswer:"
doc_to_target: "{{answer}}"
generation_kwargs:
  until:
    - "Question:"
    - "</s>"
    - "<|im_end|>"
  do_sample: false
  temperature: 0.0
num_fewshot: 5
filter_list:
  - name: "strict-match"
    filter:
      - function: "regex"
        regex_pattern: "#### (\\-?[0-9\\.\\,]+)"
      - function: "take_first"
  - name: "flexible-extract"
    filter:
      - function: "regex"
        group_select: -1
        regex_pattern: "(-?[$0-9.,]{2,})|(-?[0-9]+)"
      - function: "take_first"
metadata:
  version: 3.0

왜 두 개인가. strict-match는 모델이 지정 형식(#### 숫자)을 지켰을 때만 점수를 준다. flexible-extract는 출력 어디에 있든 마지막 숫자를 답으로 본다. 두 점수의 차이가 곧 "모델이 못 푼 것"과 "형식을 안 지킨 것"의 분리다. 하나만 재면 이 둘이 섞여서 원인 분석이 불가능해진다.

로컬 데이터셋 쓰기

dataset_kwargs가 datasets.load_dataset에 그대로 전달되므로 로컬 파일을 지정할 수 있다.

# JSON 파일
dataset_path: json
dataset_name: null
dataset_kwargs:
  data_files: /path/to/my/json

# 스플릿별 arrow 파일
dataset_path: arrow
dataset_kwargs:
  data_files:
    train: /path/to/arrow/train/data-00000-of-00001.arrow
    validation: /path/to/arrow/validation/data-00000-of-00001.arrow

# save_to_disk()로 미리 받아 둔 데이터셋
dataset_path: hellaswag
dataset_kwargs:
  data_dir: hellaswag_local/

저장소 밖에 YAML을 두려면 --include_path /경로로 알려주거나 --tasks /경로/파일.yaml을 직접 넘긴다.

13함정과 주의사항

YAML에서 개행 문자
홑따옴표는 이스케이프를 처리하지 않는다. until: ['\n']은 역슬래시와 n 두 글자로 파싱된다. 실제 개행이 필요하면 겹따옴표를 써야 한다 — until: ["\n"]. 정지 조건이 안 먹는 원인 대부분이 이것이다.
--limit으로 낸 점수는 점수가 아니다
문서에 테스트 전용이라고 명시돼 있다. 동작 확인용이지 보고용이 아니다.
GGUF 모델은 토크나이저를 따로 줘야 한다
별도 토크나이저를 주지 않으면 HF가 GGUF 파일에서 토크나이저를 복원하려 시도하는데, 몇 시간이 걸리거나 무한정 멈출 수 있다. tokenizer=/path/to/tokenizer를 함께 넘기면 초 단위로 끝난다.
추론(thinking) 모델
CoT 트레이스를 채점 전에 잘라내려면 enable_thinking=True와 think_end_token을 함께 넘긴다. think_end_token은 필수이며, 값은 모델의 tokenizer_config.json에서 확인한다. vLLM·SGLang에서는 문자열만 되고, HF 백엔드는 토큰 ID(정수)도 받는다 — 그 토큰 문자열이 본문에 등장하는 경우를 피하려면 ID가 안전하다. 이 옵션은 생성형 태스크에만 쓸 수 있다.
챗 API로는 절반의 태스크만 돌아간다
로그확률을 주지 않는 모델은 generate_until만 가능하다. 객관식 벤치마크 점수를 챗 API로 재려면 태스크가 생성형으로 정의돼 있어야 한다.
상용 챗 API 평가 시
먼저 --limit 10으로 몇 개만 돌려 답 추출과 채점이 의도대로 되는지 눈으로 확인하라고 권고한다. 답 형식이 어긋나면 모델 성능과 무관하게 0점이 나온다.
논문 간 비교
같은 도구로 냈더라도 프롬프트·few-shot 수·태스크 버전이 다르면 비교할 수 없다. 결과에 versions와 n-shot이 함께 기록되는 이유다.

14폐쇄망에서 쓰기

이 절은 저장소 문서에 없는 내용으로, 외부 네트워크가 차단된 환경에 대입한 검토다.

유리한 점

  • 라이선스가 MIT다. 사내 반입·수정·재배포에 제약이 적다.
  • 이미 운영 중인 vLLM 서버를 그대로 붙일 수 있다. local-completions 모델 타입에 base_url만 내부 주소로 지정하면 된다. 평가용으로 모델을 따로 로드할 필요가 없다.
  • 로컬 데이터셋이 정식 지원된다. dataset_path: json + dataset_kwargs.data_files 조합으로 사내에 반입한 JSON을 그대로 태스크로 만들 수 있다.
  • 기본 의존성이 가볍다. torch·transformers 없이 코어만 설치할 수 있어 오프라인 휠 미러링 부담이 작다.

먼저 해결해야 할 것

  • 기본 태스크는 전부 HF Hub에서 데이터셋을 받는다. arc_easy의 dataset_path: allenai/ai2_arc처럼 Hub 식별자가 하드코딩돼 있다. 폐쇄망에서는 필요한 데이터셋을 미리 받아 save_to_disk()로 내려 두고 data_dir로 가리키도록 각 YAML을 고쳐야 한다. 214개 전부가 아니라 실제로 쓸 몇 개만 골라 반입하는 것이 현실적이다.
  • 일부 태스크는 임의 파이썬 코드를 실행한다. --confirm_run_unsafe_code가 필요한 태스크가 그것이다. 반입 심사 대상이므로 어떤 태스크가 여기 해당하는지 먼저 확인해야 한다.
  • --trust_remote_code는 기본적으로 꺼 둘 것. Hub에서 코드를 받아 실행하는 옵션이라 폐쇄망 정책과 충돌한다.
  • W&B·Zeno·HF Hub 로깅 기능은 쓸 수 없다. 결과는 --output_path의 JSON으로만 남기고, 시각화는 자체 도구로 붙여야 한다.

이미 자체 하네스가 있다면 — 무엇을 가져올 것인가

이 도구는 모델의 일반 능력을 재는 쪽이고, 도메인 골든셋으로 우리 코드베이스에서 잘 도는지를 재는 자체 하네스와는 층위가 다르다. 대체 관계가 아니라 순서 관계다 — 모델 후보를 좁힐 때 이 도구를, 좁힌 뒤 실제 작업 적합성을 볼 때 자체 하네스를 쓴다.

다만 설계에서 가져올 만한 것이 세 가지 있다.

  1. 이중 필터 파이프라인 — 엄격 추출과 느슨한 추출의 점수를 함께 내면, 모델이 못 푼 것과 형식을 안 지킨 것이 분리된다. 자체 골든셋 채점에 바로 이식할 수 있다.
  2. 태스크 버전 기록 — 결과에 versions를 함께 남기는 규약. 골든셋을 고칠 때마다 버전을 올리지 않으면 과거 점수와의 비교가 조용히 무의미해진다.
  3. 설정 파일과 결과의 동시 커밋 — 실행 조건을 YAML로 고정해 결과와 같이 버전 관리하는 방식.

15이 도구가 하지 않는 일

항목실제
에이전트 평가도구 사용, 다단계 작업, 파일 조작 같은 에이전트 행동을 평가하는 도구가 아니다. 단발 요청·응답 채점이 대상이다
멀티모달hf-multimodal·vllm-vlm 모델 타입과 mmmu 태스크가 프로토타입으로 있지만, 프로젝트 스스로 lmms-eval을 권한다
멀티노드 실행네이티브 미지원. 외부 추론 서버를 쓰거나 직접 통합해야 한다
모델 학습·튜닝범위 밖. 평가만 한다
점수의 절대적 해석도구가 보장하는 것은 "같은 절차"이지 "옳은 절차"가 아니다. 벤치마크 자체의 타당성은 별개 문제다
