# 하네스 적합성 평가 — 경량 + Evaluator 제어 + 평가 게이트 범용성

> 작성 2026-09-06 · v0.10.x 기준 · 분석(코드 변경 없음)
> 질문: 이 하네스가 "경량 + eval 제어/게이트를 갖춘 범용 하네스"에 맞나? 웹(DB 연동)·모바일(백엔드 API 연동) 개발에서 없을 때보다 품질·안정성이 오르나? 무엇이 부족하고 무엇이 과한가.

## 0. 먼저 — 하네스가 실제로 보장하는 것 (성격 규정)

핵심 구분: 이 하네스는 **과정 품질(process floor)**을 강제하지 **도메인 정합성(correctness)**을 보장하지 않는다.

- **강제(결정적, exit 2)**: 보호 경로·시크릿 쓰기 차단, 위험 git·파괴적 SQL·마이그레이션 수정 차단, 변경 스택 **빌드·타입·린트·테스트 통과** 없이는 완료 선언 불가, 검증 루프 미달 시 완료 차단.
- **측정(숫자)**: 골든셋 pass@k/pass^k 추이·회귀, 빌드 건강도 채점표(`eval-score`), 가드레일 자기평가(`redteam`).
- **강제 못 하는 것**: "이 코드가 요구사항을 맞게 구현했나"는 사람이 쓴 테스트·골든셋 케이스·리뷰가 있을 때만 잡힌다. 앱이 런타임에 실제로 도는지는 **e2e를 직접 쓴 경우에만**.

즉 "훨씬 안정적인 동작을 **보장**"이 아니라 "안 짠 테스트·안 막은 실수의 바닥을 **올린다**". 이 전제로 평가한다.

## 1. 평가표 — 웹 개발 (DB 연동 포함)

각 항목: 없을 때(설득만) vs 하네스(강제). 점수 = 하네스가 그 차원을 얼마나 결정적으로 든든하게 하나(0 없음 · 1 규칙/권고 · 2 게이트 강제 · 3 게이트+측정).

| # | 품질 차원 | 없을 때 | 하네스 | 근거 | 점수 |
|---|---|---|---|---|---|
| W1 | 시크릿이 코드·`.env`·커밋에 새는가 | 확률적 | `.env`·prod·시크릿 리터럴 쓰기 exit 2 + pre-commit 2차 | `pretool-guard`·`lib-protected`·`redteam` 29/29 | **3** |
| W2 | 파괴적 DB 조작(`DROP`/`TRUNCATE`/`WHERE` 없는 `DELETE`) | 실행됨 | DB 클라이언트 명령 차단 | `safety.md`·`pretool-guard` DANGER_SQL | **2** |
| W3 | 기존 마이그레이션 변조 | 수정함 | 보호 경로 차단, 새 버전만 | `safety.md`·guard·골든셋 `guard-migration-blocked`(required) | **3** |
| W4 | 빌드·타입 깨진 채 "완료" | 자주 | 변경 스택 컴파일·tsc 실패 시 완료 차단 | `stop-verify` + `typescript.sh`/`java-spring.sh` | **2** |
| W5 | 테스트 없이/실패한 채 완료 | 흔함 | 테스트 실패 exit 2, 버그=재현 테스트 요구 | `stop-verify`·골든셋 `craft-*`·`eval-score` G2 | **2** |
| W6 | N+1·페이지네이션·인덱스·트랜잭션 | 리뷰 운 | 규칙 로드(권고) + 상세본, **강제는 프로젝트 테스트 몫** | `database.md`·`dev-stack-orm.md` | **1** |
| W7 | 입력 검증·SQLi·XSS | 리뷰 운 | Zod/`@Valid` 규칙 + 파라미터 바인딩 권고. 미검증 HTML 렌더 금지(문장) | `react-next`·`java-spring` patterns·`security.md` | **1** |
| W8 | 인증/인가가 엔드포인트에 실제로 걸렸나 | 미검증 | (Java 게이트웨이면) 통합 테스트 SC 강제 · `security-reviewer` | `gateway-testing.md`(GATE-04)·에이전트 | **2**(Java) / **1**(그 외) |
| W9 | 커버리지 하락 | 안 봄 | 80% 규칙 + `eval-score` coverage 항목(리포트 있을 때) | `common/testing.md`·`eval-score` | **1** |
| W10 | 회귀(멀쩡하던 게 깨짐) | 프로덕션서 발견 | 골든셋 `/eval` 추이·`required` 거부권·CI stale/regressed | `eval-gate`·`carve-eval` | **2**(골든셋 유지 시) |
| W11 | 상태 소실(긴 작업·세션 교체) | 증발 | 핸드오프 자동 저장·복원 | `session-handoff` | **2** |
| W12 | 런타임 실제 구동(앱이 진짜 뜨나) | 손검증 | **없음** — 단위/통합 테스트만. e2e는 직접 써야 | — | **0→1**(골든셋 `cmd_exit0`로 가능) |

**웹+DB 종합**: 시크릿·파괴적 SQL·마이그레이션·빌드/테스트 게이트에서 명확한 개선(없을 때 대비 바닥이 크게 오름). DB 정합성·인증 실효성은 **Java 스택에서 가장 강하고**(게이트웨이 통합 테스트), TS/Node에서는 규칙 권고 수준이라 사람의 테스트 작성에 의존. → **"쓰면 낫다"는 참. 단, 강제력은 스택별로 편차.**

## 2. 평가표 — 모바일 앱 (백엔드 API 연동)

| # | 품질 차원 | 없을 때 | 하네스 | 근거 | 점수 |
|---|---|---|---|---|---|
| M1 | 모바일 스택 자체 게이트(Swift·Kotlin·Dart) | — | **없음** — 지원 스택 아님 | 팩 6종에 모바일 없음 | **0** |
| M2 | React Native / Expo(=TS) | — | typescript 팩(tsc·lint·test)으로 **부분** 커버 | `typescript.sh` | **1~2** |
| M3 | Flutter(Dart) | — | 없음. `GUIDE §8.2`로 스택 파일 1개 추가 필요 | — | **0** |
| M4 | API 클라이언트 계약(응답 스키마·에러 코드) | 리뷰 운 | **클라 측 규칙 없음**. 서버 측 게이트웨이 SC만 있음 | gateway는 서버 | **0~1** |
| M5 | 네트워크 견고성(타임아웃·재시도·오프라인·백오프) | 손검증 | **규칙·게이트 없음** | — | **0** |
| M6 | 토큰 저장·갱신(모바일 시크릿 스토어) | 리뷰 운 | 시크릿 리터럴 스캔은 되나 keychain/keystore 패턴 없음 | `security.md`(일반) | **1** |
| M7 | 백엔드가 API 계약을 지키나(서버 쪽) | 미검증 | Java면 게이트웨이 통합 테스트, 그 외 스택은 규칙 권고 | `gateway-testing.md` | **2**(Java 백엔드) |
| M8 | 시크릿·빌드·상태·회귀(공통 축) | — | 웹과 동일하게 유효(W1·W4·W10·W11) | 위 표 | **2~3** |

**모바일 종합**: **클라이언트 측은 사실상 미지원.** RN이면 TS 팩으로 반쪽, Flutter/네이티브면 게이트 0. 백엔드 API(특히 Java/Spring)를 이 하네스로 개발하면 서버 측 안정성은 확실히 오른다(게이트웨이 5기능 통합 테스트). 하지만 "모바일 앱이 백엔드 호출로 안정 동작"의 **모바일 절반은 하네스가 잡아주지 않는다** — 네트워크 견고성·API 계약·토큰 스토어 규칙·스택 게이트가 없다.

## 3. 부족한 것 (범용 하네스로서의 갭)

| 우선 | 갭 | 영향 | 근거 |
|---|---|---|---|
| **높음** | **모바일 스택 부재** — Swift·Kotlin·Dart 팩 없음, RN도 반쪽 | 모바일 시나리오에서 게이트가 거의 안 뭄 | 팩 6종 = TS·java·py·go·rust·db |
| **높음** | **API 계약(클라↔서버) 검증 규칙 없음** — OpenAPI/스키마 대조·응답 타입 안전·에러 코드 계약 | 웹·모바일 모두 "연동이 실제로 맞나"를 못 잡음 | 게이트웨이는 서버 5기능만 |
| **높음** | **런타임/e2e 게이트 부재** — 앱이 실제로 뜨는지, 핵심 유저 플로우가 도는지 | "동작 보장"의 핵심이 빠짐. 골든셋 `cmd_exit0`로 우회 가능하나 표준 게이트 아님 | `stop-verify`=단위/통합 |
| 중 | **네트워크 견고성 규칙 없음** — 타임아웃·재시도·백오프·오프라인·멱등 | 분산 호출 구조의 실패 모드를 규칙이 안 다룸 | rules에 없음 |
| 중 | **커버리지 강제가 프로젝트 설정 의존** — 하네스가 임계를 소유하지 않음(80은 문장) | 팀이 vitest/jacoco 임계를 안 걸면 무력 | `common/testing.md` 권고 |
| 중 | **DB 정합성 강제가 TS/Node에서 약함** — N+1·트랜잭션·인덱스가 규칙(문장)뿐 | Java는 archunit로 일부 강제, 나머지는 권고 | `database.md` 권고형 |
| 낮 | **골든셋이 day-0엔 비어 있음** — `/eval` 실효는 1~2주 뒤 | 초기엔 평가 게이트가 사실상 미가동 | `eval-init` 설계상 |

## 4. 과한 것 (경량성 대비 무게)

| 판정 | 항목 | 근거 |
|---|---|---|
| **과함(소형·단일 스택엔)** | Fable 팀 오케스트레이션(에이전트 4종 + 워크플로) | 멀티모듈·대규모용. 소형 웹/앱엔 `/carve-harness-create`가 prune 권고 |
| **과함(초기엔)** | 평가 파이프라인 전체(eval-run·trend·gate·score·redteam 7스크립트) | 골든셋 유지 인력 없으면 미가동 자산. 단 훅은 무해(호출 안 하면 0비용) |
| 경계 | 골든셋 스타터 20건·judge 예시 5종 | 언어팩과 함께 설치. 안 쓰면 디스크만 차지(상시 로드 아님 → 토큰 0) |
| **적정** | 3기둥 게이트(가드·stop-verify·핸드오프)·감사·언어팩 선택 | 경량 코어. 미선택 팩은 파일 자체가 없음 |
| **적정** | 규칙 슬림본 상시 로드 | 스택별 ~30~60줄, 상세본은 `docs/`로 분리(토큰 절약) |

> 경량성 판정: **코어는 경량이 맞다.** 상시 로드는 슬림 규칙뿐, 미선택 언어팩·안 부르는 평가 스크립트는 토큰 0. "과함"은 대부분 **옵트인/prune 가능** — 기본 설치가 무겁다기보다, 전량 설치 후 안 쓰면 자산이 노는 형태. `HARNESS_PACKS`·`/carve-harness-create`가 이걸 조절한다.

## 5. 결론

- **범용 하네스 성격 부합도: 부분 참.** "경량 + eval 제어 + 평가 게이트"의 골격은 갖췄고, **백엔드(특히 Java/Spring) + 웹 + DB** 시나리오에선 없을 때보다 확실히 품질 바닥이 오른다(시크릿·파괴적 SQL·마이그레이션·빌드/테스트·회귀 게이트).
- **"동작을 보장"은 과대. "실수의 바닥을 올리고 회귀를 숫자로 잡는다"가 정확.** 요구사항 정합성·런타임 구동은 사람이 쓴 테스트·골든셋·e2e가 있을 때만 잡힌다.
- **가장 큰 미달: 모바일 클라이언트·API 계약·런타임 e2e.** 모바일 앱+백엔드 연동의 "모바일 절반"과 "연동이 실제로 맞나"를 표준 게이트로 못 덮는다.
- **가장 큰 강점: 결정적 안전 게이트 + 스택별 검증 + 회귀 측정의 통합**, 그리고 미사용분이 토큰을 안 먹는 경량 구조.
