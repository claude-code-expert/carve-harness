# `/eval-init` — 평가·품질 게이트 확정 인터뷰 (시나리오 + 개발 계획)

> 상태: **계획(미구현)** · 작성 2026-08-06 · 승인 전 구현 착수 금지(AGENTS.md §8).
> 문제: 채점 엔진(`carve-eval.js`·`eval-state.sh`)과 절차 지식(`eval-goldenset` SKILL)은 있는데,
> **"매뉴얼 → 실제 파일"** 사이가 사람 손에 맡겨져 있다. 실측: `specs/goldenset/` 비어 있음,
> `.github/workflows/*`에 eval 참조 0건. 결과적으로 `/eval`은 대부분의 설치본에서 죽은 기능이다.

## 설계 원칙 (이걸 어기면 골든셋이 무의미해진다)

1. **자동 확정 금지.** 에이전트가 혼자 만든 케이스는 자기가 이미 통과하는 것만 담는다(자기강화).
   기계적 분석·초안은 에이전트, **크리티컬 경로·실패 소재·엄격도는 사람이 확정**한다.
2. **편입 전 궤적 검사 필수.** 케이스마다 1회 실행 후 에이전트 궤적(우회했나)과 verifier 궤적
   (프록시만 쟀나)을 사람이 본 것만 골든셋에 들어간다(`eval-goldenset` §verifier 반복 절차).
3. **상태 assert 우선.** "했다"는 텍스트가 아니라 파일·명령 exit로 채점한다.
4. **스킬이지 워크플로가 아니다.** 워크플로 에이전트는 백그라운드라 질문할 수 없다 —
   대화형 확정은 메인 세션 스킬에서만 가능하다.
5. **기존 자산 불가침.** 골든셋이 이미 있으면 덮어쓰지 않고 증설 모드로 간다.

## 이름

`eval-init` — `/eval` 옆에 서고, 입력이 짧다. 범위는 평가 게이트(골든셋·k·회귀 delta)와
품질 게이트(커버리지 임계·checklist 임계·CI 강도) **둘 다**이므로 설명문에 명시한다.
대안 `quality-gates`는 기존 `/eval` 계열과의 인접성이 떨어져 기각.

# 1. 시나리오 (Next.js + Drizzle 커머스 프로젝트, 하네스 설치 2주차)

## S0. 사전 점검 — 질문 없음

- `.claude/harness-manifest.txt` 확인. 없으면 **중단**("설치된 하네스가 아닙니다").
- `git status --porcelain` — dirty면 경고만(결과를 diff로 검토·롤백 권장).
- `specs/goldenset/*.json` 존재 여부 → 있으면 **증설 모드**(기존 케이스 유지, 추가만).

## S1. 프로젝트 분석 — 질문 없음, 근거와 함께 1문단 요약

수집 축(전부 읽기 전용):

| 축 | 방법 | 쓰임 |
|---|---|---|
| 스택·러너·커버리지 도구 | `package.json`·`pyproject.toml`·`go.mod` 등 | 케이스의 `cmd_exit0` 형태 결정 |
| 진입점 목록 | 라우트·핸들러·CLI 서브커맨드 파일 스캔 | 크리티컬 경로 **후보** |
| 수정 빈도 상위 | `git log --since=3.months --name-only` 집계 | 자주 깨지는 곳 = 케이스 1순위 |
| 하네스 차단 이력 | `logs/*.jsonl`의 `.decision=="block"` 집계 | 실제 막아낸 실수 패턴 |
| 기존 테스트 | 테스트 파일 수·커버리지 실측(가능하면) | 커버리지 임계 제안의 근거 |
| CI | `.github/workflows/` | 게이트 강도 선택지 조정 |

출력 예:

```
분석: Next.js 16 + Drizzle, vitest(커버리지 도구 있음, 현재 라인 62%), CI 있음(ci.yml).
      진입점 23개. 최근 3개월 수정 빈도 상위 — src/api/checkout(11회) · src/auth/session(8회)
      · src/orders/cancel(6회). 하네스 차단 이력 — .env 쓰기 시도 4회, 파괴적 SQL 1회.
      기존 골든셋 없음 → 신규 생성 모드.
```

## S2. 인터뷰 A — 무엇이 중요한가 (사람만 아는 것)

**Q1. 크리티컬 경로** (멀티, 분석 후보 + 기타)
> "여기 깨지면 사고"인 경로를 고르세요. 3~5개 권장.
> ☑ 결제 체크아웃(수정 11회) ☐ 세션 인증(8회) ☐ 주문 취소(6회) ☐ 상품 검색 ☐ 기타…

**Q2. 최근 실제 실패** (자유 입력, 없으면 skip 허용)
> 최근 실제로 터진 버그·재발 이슈가 있나요? **있다면 그 재현이 최고의 첫 케이스입니다.**
> (없으면 합성 케이스로 시작하되, 2주 뒤 트레이스 마이닝으로 교체한다고 안내)

**Q3. 도메인 불변식** (자유 입력 3개, `CLAUDE.md` 도메인 규칙에 기록)
> "이건 절대 안 된다" 3개. 예: "주문 금액 음수 불가", "결제 승인 없이 배송상태 변경 금지".
> → 승인 시 `CLAUDE.md`에 append(기존 내용 보존, 덮어쓰기 금지).

## S3. 인터뷰 B — 얼마나 엄격한가 (품질 게이트)

**Q4. 커버리지 임계** — 현재 실측(62%)을 보여주고: 유지(62) / 권장(80, `common/testing.md` 기준) / 미설정
**Q5. 검증 루프 임계** — 95 기본(권장) / 90 완화 / 100 엄격 → `CARVE_CHECKLIST_FLOOR`
**Q6. 반복 신뢰도** — k=1(빠름) / **k=3(권장)** / k=5(엄격), 회귀 delta 3pt 기본
**Q7. 게이트 강도** — 로컬 리포트만 / PR 코멘트 / **CI 차단**
> CI 차단은 **골든셋을 유지할 사람이 있을 때만** 권장(유지 안 하면 우회 압력만 생긴다)고 고지.

## S4. 초안 생성 + 궤적 검사 — 두 번째 인터랙션 지점

케이스 3~5개 초안. 상태 assert 우선, `setup`으로 격리 워크디렉토리 구성:

```json
{
  "id": "checkout-idempotent",
  "prompt": "결제 확정 API에 멱등키 처리를 추가하고 테스트를 통과시켜라.",
  "setup": "git init -q . && cp -r <fixture>/checkout . && npm i --silent",
  "k": 3,
  "assert": [
    { "type": "cmd_exit0", "value": "npx vitest run checkout --silent" },
    { "type": "file_contains", "value": "src/api/checkout/route.ts::idempotencyKey" },
    { "type": "git_diff_contains", "value": "idempotency" }
  ]
}
```

케이스별 1회 실행 후 **양쪽 궤적 표**를 제시:

| 케이스 | 에이전트 궤적 | verifier 궤적 | 판정 |
|---|---|---|---|
| checkout-idempotent | 라우트 수정 + 테스트 추가 | 3 assert 전부 상태 기반, 우회 없음 | 편입? [Y/n] |
| auth-session-expiry | **테스트만 고침**(구현 미변경) | `cmd_exit0`이 통과 — **프록시 충족** | 수정 필요 |

리워드 해킹 카탈로그(허위 주장·프록시 충족·정답 노출·과잉 충족)로 자동 점검 후 의심 케이스는
표에 사유를 달아 **사람이 결정**하게 한다. **미승인 케이스는 파일에 들어가지 않는다.**

## S5. 확정·배선·요약

1. `specs/goldenset/<suite>.json` — 승인 케이스만 기록
2. `CLAUDE.md` 도메인 규칙 append(승인분만)
3. 게이트 강도별 산출:
   - 로컬: 안내만
   - PR 코멘트: `.github/workflows/eval.yml`(리포트, 항상 exit 0)
   - CI 차단: 같은 워크플로 + baseline 대비 delta 초과 하락 시 **exit 비0**
4. `/eval` 1회 실행 → `specs/eval-score.json`에 **baseline** 기록
5. 요약표: 확정 케이스 수·임계값 3종·게이트 강도·다음 액션(2주 뒤 트레이스 마이닝)
6. `specs/DECISIONS.md`에 결정 기록(임계값과 그 근거 — 나중에 "왜 80이었나"를 답할 수 있게)

# 2. 개발 계획 (단계 → SC)

> 각 단계는 **검증 가능한 완료 기준(SC)** 을 갖는다. SC 미충족은 완료가 아니다.

| # | 단계 | 산출물 | 완료 기준(SC) |
|---|---|---|---|
| P0 | 설계 확정 | 이 문서 | 시나리오·질문 7종·산출물 스펙에 대한 사용자 승인 1회 |
| P1 | 스킬 골격 + 분석 | `.claude/skills/eval-init/SKILL.md` | 하네스 미설치 디렉토리에서 **중단**; 설치본에서 분석 요약이 근거 파일 경로와 함께 출력되고 **질문 전 정지** |
| P2 | 인터뷰 A/B | 같은 파일 | 7문항이 순서대로 제시되고, 미응답·"기타" 입력이 기본값으로 안전 처리; 답변이 결정 레코드로 보존 |
| P3 | 초안 생성기 | 같은 파일 + 픽스처 | 생성된 JSON이 `carve-eval.js`의 `GOLDENSET_SCHEMA`를 통과하고, 상태 assert 비율 ≥ 50%; 알 수 없는 assert 타입 0건 |
| P4 | 궤적 검사 관문 | 같은 파일 | 케이스별 궤적 표가 제시되고, **미승인 케이스가 파일에 기록되지 않음**(테스트로 증명) |
| P5 | 게이트 배선 | `.github/workflows/eval.yml` 템플릿 | 리포트 모드는 항상 exit 0; 차단 모드는 delta 초과 하락 시 exit 비0(스텁 점수로 재현) |
| P6 | 회귀 테스트 | `.claude/hooks/tests/eval-init.test.sh` | 신규 스위트 green + 전 스위트 green(현행 19→20 스위트) + `/harness-audit` PASS 유지 |
| P7 | 문서 | README ko/en · GUIDE · `eval-goldenset` SKILL | 스킬 인벤토리 9→10 반영, `eval-goldenset`에 "실행기는 `/eval-init`" 포인터, day-0 부트스트랩 절과 중복 제거 |

## 테스트 전략 (P6 상세)

대화형이라 질문 자체는 자동 테스트가 어렵다 → **질문을 제외한 결정론 부분만** 어서션한다:

- 하네스 미설치 → 중단(exit 비0 또는 명시적 중단 보고)
- 분석 단계가 읽기 전용(픽스처 리포에 쓰기 발생 0건)
- 답변 픽스처(JSON) 주입 → 생성 골든셋이 스키마 통과
- 미승인 케이스 제외 로직
- 기존 골든셋 존재 시 덮어쓰기 0건(증설만)
- 워크플로 템플릿의 차단/리포트 모드 exit 코드

## 리스크와 선제 결정

| 리스크 | 대응 |
|---|---|
| 합성 케이스만 남아 "이미 아는 문제"에 치우침 | S5 요약에 "2주 뒤 트레이스 마이닝 교체" 액션 고정 명시 |
| CI 차단을 켰는데 골든셋 방치 → 우회 압력 | Q7에서 유지 인력 확인 후에만 차단 모드 제시 |
| 질문 피로(7문항) | Q2·Q3는 skip 허용, 나머지는 기본값 제시로 엔터 통과 가능 |
| 스킬 자동 발동으로 파괴적 동작 | `disable-model-invocation: true`(carve-harness-create 선례) |
| 기존 골든셋 파괴 | S0 증설 모드 분기 + P6 테스트로 고정 |

## 범위 밖 (이번에 하지 않음)

- 골든셋 케이스 **자동 확정**(설계 원칙 1 위반)
- 다중 suite 오케스트레이션·케이스 자동 증식
- `/eval` 채점 엔진 변경 — 이미 동작하므로 손대지 않는다
